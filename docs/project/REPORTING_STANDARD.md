# BOYA Agent 改进与汇报标准

版本：1.0
状态：当前项目工作标准
用途：统一代码改进、性能优化、用户体验调整、测试、部署和风险的记录方式。
更新时间：2026-09-04

本标准规定工程变更记录的结构、证据和状态边界。它不替代项目状态、架构、安全、配置和部署文档；这些文档仍然各自负责对应主题。

## 一、汇报中的状态词

| 状态 | 可以说明什么 | 不能说明什么 |
| --- | --- | --- |
| 已完成 | 当前版本已经有对应代码或文档改动 | 不等于测试通过或生产可用 |
| 已验证 | 指定命令、页面操作、接口请求或演练已经实际执行 | 不等于所有场景都验证 |
| 已部署 | 指定版本已进入明确环境，并通过部署检查 | 不等于真实业务效果已确认 |
| 待验证 | 已有实现，但缺少必要的测试或外部演练 | 不能写成已稳定 |
| 未运行 | 本次没有执行该检查 | 不能引用为本次结果 |
| 阻塞 | 有明确原因导致当前工作无法继续 | 不能用来掩盖尚未排查的问题 |
| 默认关闭 | 代码存在，当前配置没有启用 | 不等于功能不存在 |
| 实验能力 | 可以运行，但风险或验证范围不足 | 不作为稳定承诺 |
| 历史方案 | 过去曾使用或讨论过 | 不代表当前实现 |
| 待确认 | 需要业务、技术、运维或用户作决定 | 不应由汇报人擅自补结论 |

## 二、证据分级

汇报中要明确证据类型：

1. **代码/配置事实**：来自当前工作区文件、配置或版本记录。
2. **自动化验证**：来自实际运行的测试、编译、类型检查或静态检查。
3. **环境验证**：来自指定主机、服务、接口、页面或外部渠道的实际操作。
4. **生产观察**：来自真实流量、真实课程、真实通知或上线后日志。
5. **建议或推测**：尚未实施或没有足够证据支持的判断。

证据不能跨级替代。例如，代码中有邮件发送函数，只能证明代码事实；不能证明 SMTP 已经可达。服务器返回健康检查成功，只能证明服务探活正常；不能证明真实课程已经抓取成功。

## 三、工程汇报结构

每次主要变更按以下结构记录：

### 1. 执行摘要

用一至三句话说明变更结果、当前发布状态和最重要的限制。不要用“全面完成”“彻底解决”等无法由证据支持的结论。

### 2. 基线与变更范围

写明：

- 分支和提交；
- 工作区是否干净；
- 未跟踪或未修改的用户文件；
- 相关代码和文档现状；
- 测试环境和依赖状态；
- 当前线上版本（如果有实际核对）。

### 3. 变更集与设计依据

按功能或风险分组，说明改动对象、要解决的问题、设计依据、兼容处理和相关文件。不要只罗列文件名。

### 4. 验证证据

每项写明检查方式和结果：

```text
检查项：
方式/命令：
环境：
时间：
结果：
证据或日志位置：
```

没有执行的项目写“未运行”，并说明原因或下一步。

### 5. 发布记录

只有实际部署后才填写“已部署”。至少包括：

- 目标主机或环境；
- 域名或访问入口；
- 分支和提交；
- 数据库迁移；
- 服务重启和状态；
- 健康检查；
- 关键页面/API；
- 邮件、Telegram、自动选课等外部能力是否启用；
- 观察窗口和回滚方式。

### 6. 风险、约束与未决事项

按“风险、影响、当前缓解、解除条件”写清楚。不要把“以后再看”当作风险说明。

### 7. 后续动作与验收条件

只列可执行动作，并给出完成条件。例如“补充通知重复投递测试，要求服务重启后同一幂等键仍只产生一条成功记录”。

## 五、报告语言规则

- 第一段先写结论，不先写漫长过程。
- 一个要点只表达一个事实或动作。
- 数字带时间、环境和统计口径。
- “全部通过”“稳定”“已上线”“性能提升”等结论必须有范围和证据。
- 面向普通用户时，把内部状态改成动作、结果或限制。
- 面向工程人员时，保留必要的文件、接口、提交和命令，但同时解释它们的作用。
- 不写完整邮箱、密码、验证码、Cookie、SMTP 密码、校园账号或完整 token。
- 历史结果注明日期；历史结果不能代替当前验证。
