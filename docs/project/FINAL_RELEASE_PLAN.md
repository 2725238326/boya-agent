目标是在不向真实用户发送邮件、不启用 Telegram 和自动选课的前提下，完成新版的代码验证、页面验收、生产部署和运行观察。上线判断以可重复的检查结果为依据，不把“服务能启动”当作业务结果。

## 上线前必须解决的事项

### 1. 邮件发送边界

当前数据库开关已经阻止自动课程邮件、每日摘要、选课提醒和自动选课结果邮件，并且没有待发送邮件任务。最终版还必须在底层 SMTP 发送函数增加一个明确的总开关，例如 `EMAIL_DELIVERY_ENABLED=false`，使以下路径在测试期都不会连接 SMTP：

- 邮箱验证和登录邮件；
- 课程通知、摘要和选课提醒；
- 自动选课结果邮件；
- 管理员测试邮件、手动推送和站点调整通知。

总开关必须有单元测试。测试只允许使用模拟 SMTP 或本地邮件预览，不得把真实收件地址、真实密码或真实 SMTP 连接放入自动化检查。重新启用邮件必须是单独的配置变更，并记录启用时间、范围和回退方式。

### 2. 依赖和验证环境

本地默认解释器目前不能完整收集测试，`D:\\Anaconda\\python.exe` 和 CI 可以通过。最终版前应固定一个推荐入口，并明确记录未运行的解释器；不能把不同解释器的结果合并成一个“全部通过”。

### 3. 用户路径验收

使用固定课程样例和无课样例检查：

- 首次打开、刷新、重复刷新和请求超时；
- 当前无课、筛选无结果、已满、未开选、已结束和数据异常；
- 课程详情、筛选、提醒、暂停、恢复和退出；
- 窄屏、键盘焦点、减少动画和错误提示；
- 管理员页面与普通用户页面的权限边界。

每个场景都记录页面文字、按钮行为、接口状态和控制台错误。无课时不能显示成系统故障；请求失败时不能显示成“没有课程”。

### 4. 抓取和 Playwright 验收

固定验证正常有课、正常无课、登录失效、上游不可用、解析失败和超时六类结果。重点检查元素/页面状态等待、有限网络空闲等待、登录重试、浏览器回收和失败诊断文件。必须确认异常快照不会覆盖可靠课程数据，并记录抓取耗时的 P50/P95 或至少一个可比较的观察窗口。

### 5. 数据库和部署验收

每次生产部署前后都要：

1. 核对目标 Git 提交和服务器工作树；
2. 生成 SQLite 一致性备份并运行 `PRAGMA integrity_check`；
3. 检查增量迁移、`notification_jobs` 表和关键索引；
4. 重启后检查本机 `/healthz`、公网健康端点、公开页面/API 和未授权管理接口；
5. 核对服务用户、Nginx、缓存策略和日志中的敏感信息；
6. 记录应用提交、数据库备份、服务状态、课程结果和外部通道开关。

## 上线判断

可以进入生产的条件：自动化验证通过；工作树和服务器提交可核对；数据库备份可读；服务和 Nginx 正常；健康、公开页面和管理边界检查通过；邮件总开关为关闭；Telegram 和自动选课为关闭；没有未处理的邮件任务；回退提交和备份位置已经记录。

暂不进入生产的情况：测试环境依赖不一致且无法说明影响；邮箱发送路径仍可能绕过总开关；页面把异常显示为无课；抓取失败可能覆盖课程数据；数据库迁移不能重复执行；服务器工作树不干净；或上线后的关键日志无法解释。

## 上线后的观察

真实课程开始后，再观察课程发现、报名窗口、名额变化、退课补位、提醒记录和页面更新时间。真实课程周期没有开始前，只能验证固定样例、无课状态和故障处理，不能把模拟结果写成实际选课效果。

邮件重新启用前，先完成邮件专项评审：收件人范围、模板文字、退订和暂停操作、重试策略、重复投递窗口、SMTP 可达性和人工回退。邮件专项工作不与本次新版上线混在一起。
