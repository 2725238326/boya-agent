## 上线前需要处理的具体问题

1. **先确定待发内容。** 当前业务代码与历史生产版本相同，没有一批尚未部署的功能升级。仅推送当前提交主要同步文档与配置样例。
2. **配置样例会触发生产。** `c0dbf96` 修改了 `config/.env.example`，命中 `deploy.yml` 的 `config/**` 触发条件；推送到 main 会进入生产工作流。提交标题为 docs 不能证明不会部署。
3. **个人功能依赖登录邮件。** 总开关 `EMAIL_DELIVERY_ENABLED=false` 会同时暂停验证码、验证和登录。可先独立评审只恢复身份邮件：启用总开关，同时保持数据库自动课程邮件、摘要、Telegram 和自动选课关闭；管理员手动发送同样会恢复可用，必须纳入发送范围审阅。
4. **故障恢复仍依赖人工。** 工作流停服后执行浏览器安装；安装失败会退出，当前 EXIT trap 只清理包并恢复邮件数据库值，不负责重新启动服务或恢复旧代码。发布前应补充并验证失败恢复流程，至少明确停服后失败如何恢复上一版本与对应依赖/浏览器。
5. **启动日志不等于抓取成功。** `main.py` 在首次抓取调用返回后输出“系统已就绪”；部署仅匹配这条日志不足以证明抓取成功，还需核对 `last_success`、抓取结果和失败原因。
6. **运行保障需核对现场配置。** 历史生产通过 systemd drop-in 设置 `MemoryMax=1300M`、`TasksMax=250`，仓库 service 样例未包含这些值。下次部署须核对 `systemctl cat` 与实际限制。历史周备份、Swap 和浏览器进程数量也需重新取证。
7. **自动备份范围不完整。** 现有部署自动备份 SQLite，但没有自动备份二维码上传目录；发布前按运维手册单独备份图片并确认可恢复。

维持现有 Nginx → 单进程 Waitress/调度器/Playwright → SQLite 部署。现阶段收益主要来自验证、故障恢复和身份邮件开放，无需先更换框架或扩展为多实例。
