## 发布推进顺序

1. 审阅当前分支，形成候选提交；功能分支运行云端 CI。确认 main 的配置样例、deploy 目录修改会触发生产。
2. 只读更新生产快照：实际提交、工作树、数据库/队列、邮件总开关与业务开关、systemd/drop-in、Nginx、内存/Swap、浏览器和备份；确认额外 venv 快照所需磁盘。
3. 完成 Linux/systemd 受控恢复演练，再发布核心代码。记录旧提交、数据库与图片备份、依赖哈希、恢复目录及发布后真实采集状态。
4. 邮件单独开放：先限定测试收件范围，EMAIL_DELIVERY_ENABLED=true 且 EMAIL_DELIVERY_SCOPE=auth；保持业务课程邮件、摘要、Telegram、自动选课关闭。验证真实 SMTP、收件箱/垃圾箱、验证码、一次性链接、登录与票据失效。
5. 真实身份邮件验收后，再单独评审课程通知开放。先核对旧任务、已过期提醒、筛选与暂停/退订，逐步扩大收件范围并观察发送失败和重复窗口。

第 1—3 步已完成，实际生产版本和验证证据见最终验收；第 4—5 步尚未执行。没有向真实用户发消息；外部发送需先确认授权测试收件邮箱，不能从升级代码已上线推断发信已开放。

## 兼容性与回退

默认生产行为保持 SMTP 和真实抓取；新增文件模式只能用于通过隔离校验的 staging。邮件 scope 未设置时保持旧 all 行为，配置样例推荐 auth；邮件总开关默认关闭。数据库无新增业务字段或删除操作。

代码回退使用审阅后的 revert。发布失败恢复旧提交和必要的 venv，不回滚数据库/outbox；旧浏览器保留。恢复目录和二维码备份当前不自动删除，验收后需要明确清单与保留策略。若恢复服务或邮件状态失败，脚本返回失败并输出人工处置提示，不能继续认定部署成功。

验证/登录邮件仍在 Web 请求内执行；单步超时不是会话总时限。数据库提交与外部 SMTP 之间仍有失败窗口，外部投递仍为至少一次语义。真实 SMTP、域名发信认证（SPF/DKIM/DMARC）、邮箱信誉和生产长时间运行需要现场证据，不能由 fake SMTP、文件预览或健康接口推断。
