# BOYA Agent 工程与发布体系

版本：1.1  
状态：当前项目工程标准  
用途：规定设计、实现、验证、发布和运行记录的统一方式。  
更新时间：2026-09-07

本文不是大型平台方案，也不要求项目引入新的基础设施。BOYA Agent 目前是单实例轻量服务，因此只采用能够降低真实风险、且可以由现有代码和 GitHub Actions 执行的工程做法。新版本候选的具体范围见 [RELEASE_CANDIDATE.md](RELEASE_CANDIDATE.md)。

## 1. 工程目标

工程质量以用户结果和运行结果衡量：

- 用户能够看到可信的课程状态，并知道下一步应做什么；
- 抓取失败不会被当成“当前没有课程”，也不会覆盖最近一次可靠数据；
- 通知失败不会阻塞课程抓取，重复执行不会无边界地重复发送；
- 每次生产变更都有版本、验证证据、回退方法和责任边界；
- 文档只描述当前事实，历史方案与待实施计划单独标记。

## 2. 变更分类

| 变更类型 | 典型内容 | 必需记录 |
| --- | --- | --- |
| 文案/样式 | 页面文字、颜色、布局、可访问性属性 | 变更说明、页面验证、截图或操作记录 |
| 行为变更 | 筛选、提醒、登录、课程状态、通知规则 | 设计说明、兼容性分析、自动化测试 |
| 数据变更 | 字段、索引、迁移、清理规则 | 数据影响、重复执行行为、备份与回退方法 |
| 外部依赖变更 | SSO、课程系统、SMTP、Telegram、域名 | 依赖假设、超时/重试、故障处理和现场验证 |
| 生产配置变更 | 服务、Nginx、环境变量、开关 | 配置差异、发布窗口、发布前后检查 |
| 目录或结构变更 | 文件移动、模块拆分、接口边界 | 独立重构变更、路径引用检查、回退方法 |

涉及用户身份、课程数据、通知发送、数据库结构或生产配置的变更，不与无关的格式化和大范围重命名混在同一个变更中。

## 3. 单个变更的生命周期

### 3.1 设计评审

在编码前写清以下内容：

1. 要解决的用户或运行问题；
2. 当前事实和证据来源；
3. 方案的输入、输出、边界和失败行为；
4. 对接口、数据、权限、性能和部署的影响；
5. 自动化验证、现场验证和回退方式；
6. 不在本次范围内的内容。

跨模块行为、数据库结构、认证边界和生产流程应增加 ADR。小型单文件修复可以在提交说明中记录，但不能省略影响和验证。

### 3.2 实现与代码审阅

每个提交只解决一个可以独立说明的问题，并同时提交对应测试或说明为什么不适合自动化测试。优先拆成以下形式：

1. 保护现有行为的测试；
2. 不改变行为的重构；
3. 新行为或性能调整；
4. 文档和发布记录。

功能变更和纯重构分开，便于审阅、定位问题和回退。提交信息使用动词和具体对象，例如 `perf: reduce unconditional scraper waits`，不要使用无法核对的“全面升级”或“体验拉满”。

### 3.3 生产发布准入条件

进入生产前必须满足：

- 工作树无未提交文件；
- 变更分支已经完成自动化检查；
- 与 `main` 的差异可解释；
- 数据库迁移可重复执行，且已明确备份位置；
- 服务启动、健康检查和关键页面/API 检查有记录；
- 邮件、Telegram、自动选课等有副作用的开关已经核对；
- 失败时可以停止发布或恢复上一版本。

当前工作流只对 `main`/`master` 的推送自动部署。功能分支只用于开发和审阅，不应绕过验证直接成为生产版本。

### 3.4 发布后观察

发布完成不等于业务结果已经确认。发布报告至少区分：

- 服务是否启动；
- 健康检查是否通过；
- 页面和接口是否可用；
- 抓取是否得到合法结果；
- 通知是否进入任务记录、是否送达；
- 是否出现错误日志、性能异常或数据异常。

真实课程、真实通知和外部登录应单独记录环境、时间和观察窗口。没有执行的项目写“未运行”。

## 4. Git 与环境边界

| 环境 | 用途 | 允许的动作 |
| --- | --- | --- |
| 本地工作区 | 编码、单元测试、静态检查 | 创建功能分支、提交、回退本地未发布提交 |
| GitHub 远端 | 审阅、自动检查、版本记录 | 功能分支推送、合并到 `main` 前完成检查 |
| 生产服务器 | 运行 `buaaboya.top` | 由发布工作流拉取指定分支；禁止在服务器直接改业务文件 |

生产服务器必须保持干净工作树。服务器上的提交、远端目标分支和发布报告中的提交必须一致。服务器凭据只承担拉取职责；需要推送时使用经过授权且可审计的远端流程，不在仓库或命令输出中保存令牌。

本项目当前生产服务已运行在功能分支版本上，但 `main` 尚未指向同一版本。由于推送 `main` 会触发自动部署，而生产通知开关仍需按既定窗口管理，合并和发布应作为一个单独的受控动作执行，不能把 Git 整理误写成已经发布。

## 5. 运行指标与目标

以下是待确认的内部目标，不是当前已经达到的结果。目标正式生效前，需要结合实际课程周期和通知需求确认统计口径。

| 领域 | 指标（SLI） | 建议目标（SLO） | 数据来源 |
| --- | --- | --- | --- |
| Web 可用性 | `/healthz` 在观察窗口内返回 200 的比例 | ≥ 99.5% | 黑盒探活、Nginx 日志 |
| 公开接口延迟 | 课程、类别和洞察接口的 P95 响应时间 | ≤ 500 ms（不含上游抓取） | 接口访问日志/基准脚本 |
| 抓取结果 | 正常结果占已开始抓取轮次的比例 | ≥ 99%（排除明确维护窗口） | `last_scrape_status`、抓取记录 |
| 数据保护 | 失败抓取覆盖可靠课程快照的次数 | 0 | 调度器日志、数据库比对 |
| 通知时效 | 任务进入 outbox 到首次成功处理的时间 | P95 ≤ 5 分钟；需按渠道确认 | `notification_jobs` |
| 用户完成任务 | 用户打开门户后能够看到课程或明确状态的比例 | 需先建立前端观测 | 页面操作和接口记录 |

指标只用于指导行动。连续超出目标时，优先处理可靠性和数据问题；没有证据支持时，不以“稳定”“实时”或“全面优化”作结论。

## 6. 运行故障处理

发现异常后按以下顺序执行：

1. 确定影响范围：用户页面、课程数据、通知、管理接口或部署流程；
2. 保存最小必要证据：版本、时间、状态值、错误摘要和关键响应；
3. 先阻止扩大影响，例如暂停有副作用的任务或停止继续发布；
4. 恢复服务或回退版本；
5. 在原因确认后提交修复和回归测试；
6. 更新运行手册、指标或设计记录，防止同一问题只靠人工记忆处理。

事故记录使用 `INCIDENT REPORT` 模板。涉及敏感数据的日志、截图、HTML、trace 和数据库备份只能放在受控位置，不进入公开提交。

## 7. 当前执行队列

按依赖关系分为三个发布阶段：

### 阶段 A：工程基线

- 归档根目录旧审计快照；
- 固定开发和 CI 依赖入口；
- 将课程抓取结果、通知任务和发布版本写入统一记录；
- 扩展高风险路径的自动化测试；
- 让功能分支、远端和生产版本可核对。

### 阶段 B：抓取与门户体验

- 用元素、页面状态和响应条件替代无条件等待；
- 正常轮次不保存大体积截图，失败时保留受控诊断资料；
- 记录抓取耗时和阶段结果，比较优化前后 P50/P95；
- 页面区分无课程、筛选无结果、已满、已过期、加载失败和需要登录；
- 通过键盘、窄屏和减少动画设置检查关键操作。

### 阶段 C：真实课程周期验证

- 在课程实际开始后验证列表变化、名额变化、退课补位和提醒时间；
- 对外部通知逐渠道记录成功、失败、重试和重复窗口；
- 以观察数据决定是否继续拆分模块或调整 SLO；
- 没有真实课程时，只验证模拟数据和故障路径，不把模拟结果写成业务效果。

每个阶段先完成自动化检查，再决定是否进入生产。阶段之间不以“大改一次”替代验证。

## 8. 参考原则

本体系参考并按本项目规模进行了裁剪：

- [Google SRE：Service Level Objectives](https://sre.google/sre-book/service-level-objectives/)：从用户关心的服务指标定义 SLI/SLO，并用错误预算辅助发布决策；
- [Google Engineering Practices：Small CLs](https://google.github.io/eng-practices/review/developer/small-cls.html)：保持变更自包含、可审阅、带测试，并把大型工作拆成多个独立变更；
- [AWS Well-Architected：Operational Readiness](https://docs.aws.amazon.com/wellarchitected/latest/operational-excellence-pillar/operational-readiness.html)：使用运行准备检查、运行手册、可观测性和小而可回退的变更；
- [GitHub Actions：Deployment Environments](https://docs.github.com/en/actions/concepts/workflows-and-actions/deployment-environments)：用环境、分支限制和保护规则约束生产发布；
- [Playwright：Actionability](https://playwright.dev/python/docs/actionability) 与 [Locators](https://playwright.dev/python/docs/locators)：优先使用稳定的用户可见定位和自动等待，诊断产物按需保存并保护敏感信息。

这些原则不构成引入 Kubernetes、Redis、消息队列或多实例部署的理由。基础设施变化必须另行证明收益、成本、迁移和回退条件。
